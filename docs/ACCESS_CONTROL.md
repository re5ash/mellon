# Роли и разрешения

## Модель

Роль — именованный набор атомарных разрешений. `key` — машинный идентификатор роли, `title` — изменяемое отображаемое название. Код проверяет `posts.manage`, а не строку `parish_admin`. Scope хранится отдельно: `global` либо `parish`. Приходские назначения требуют действующего членства и могут иметь срок окончания.

| Стартовая роль | Как получается | Область | Набор |
|---|---|---|---|
| guest | Нет сессии | Публичная | public.read |
| user | Есть сессия | Собственные данные + свой приход | public.read, profile.self, membership.request, parish.read, chat.read, chat.send, help.respond, events.attend |
| parish_admin | Явное назначение | Только заданный приход | Приходские разрешения на материалы, членство, комнаты, модерацию, аудит |
| super_admin | Явное назначение владельцем/уполномоченным | Глобальная | Все разрешения начального каталога |

Гость — отсутствие аутентификации, не автоматически создаваемая анонимная учётная запись Supabase. Guest/user определяются полем `baseline`; персональные строки назначения им не нужны. Новые права не автоматически добавляются super_admin: миграция должна сознательно определить, кому их выдавать.

## Матрица начального поведения

| Операция | guest | user | parish_admin | super_admin |
|---|---|---|---|---|
| Публичные материалы опубликованных приходов | Да | Да | Да | Да |
| Приватные материалы прихода | Нет | Свой действующий приход | Свой управляемый приход | Через права управления |
| Личные поля и дата рождения | Нет | Только свои | Только свои | Только свои через пользовательский API |
| Вступление/выход | Нет | За себя | За себя | За себя |
| Одобрение/исключение | Нет | Нет | Свой приход | Любой приход |
| Публикации/события/помощь | Чтение публичного | Чтение разрешённого | Управление своим приходом | Управление всеми |
| Групповой чат | Нет | Доступная комната своего прихода | Управление своим приходом | Управление всеми |
| Публикация в канале | Нет | Нет | Да, в своём приходе | Да |
| Роли и назначения | Нет | Нет | Нет | roles.manage |
| Уведомления | Нет | Только свои | Только свои | Только свои через пользовательский API |
| Аудит | Нет | Нет | Свой приход | Весь |

Права приложения не означают доступ владельца инфраструктуры. Владелец PostgreSQL/серверный privileged key технически имеет иной уровень доступа; в мобильный/Web-клиент он не попадает.

## Серверная проверка

SQL `app_private.has_permission(permission, parish)` читает текущие назначения из базы. UUID берётся из `auth.uid()`. Пользователь не передаёт в проверку «мой user_id» и не утверждает самостоятельно, что он администратор. Claims/metadata с именами ролей игнорируются при регистрации. Отзыв назначения применяется при следующем запросе без обновления JWT.

Все exposed-таблицы включают RLS, а гранты выданы явно, часто на отдельные изменяемые столбцы. SECURITY DEFINER используется только у небольших проверок/операций с пустым `search_path`, полными именами таблиц и явным списком EXECUTE. `app_private` не включается в Supabase API schemas. Политики строк вместе с грантами образуют серверную границу доступа, как описано в [руководстве Supabase по RLS](https://supabase.com/docs/guides/database/postgres/row-level-security).

Сервисные/secret ключи обходят RLS и предназначены для доверенного сервера. Клиент принимает publishable key либо проверенный legacy anon key; код намеренно отклоняет privileged ключи. См. [ключи Supabase](https://supabase.com/docs/guides/getting-started/api-keys).

## Основные RPC

| Функция | Проверка/действие |
|---|---|
| my_permissions | Снимок разрешений только текущего пользователя в заданной области |
| my_private_profile / update_private_profile | Только личные поля текущего аккаунта |
| request_membership | Сессия, доступность прихода, бан, одна текущая заявка/членство |
| leave_parish | Завершение своей заявки/членства и удаление локального доступа |
| review_membership | memberships.manage в соответствующем приходе и допустимый переход статуса |
| grant_role / revoke_role | Глобальное roles.manage, валидный scope |
| define_role / role_catalog | Глобальное roles.manage, проверка ключей и разрешений |
| set_parish_published | Глобальное parishes.manage |
| set_chat_member | chats.manage и действующее членство приглашённого |
| send_message | Право чтения комнаты, chat.send/channels.publish, лимит длины/частоты, nonce |
| hide_message | chats.moderate, мягкое удаление и аудит |
| mark_notification_read | Только уведомление текущего получателя |
| read_audit | audit.read для указанной области, максимум 50 записей с курсором |

Пример новой роли «Редактор» выполняется из сессии пользователя с `roles.manage`:

```sql
select public.define_role('editor', 'Редактор', 'parish', array['posts.manage']);
select public.grant_role('USER_UUID', 'editor', 'PARISH_UUID');
```

Это пример с placeholders, не готовая SQL-команда для запуска без замены значений. Нельзя включить `roles.manage` в приходскую роль. Baseline-роли изменяются только миграцией, чтобы случайная правка каталога не распространила административные возможности на всех пользователей.

## Первый супер-администратор

Никто не становится создателем только потому, что первым зарегистрировался. Зарегистрировать известный аккаунт, подтвердить его email и сверить UUID в Auth Dashboard. Затем владелец базы выполняет в одной транзакции `set_config('app.bootstrap_user_id', '<UUID>', true)` и содержимое `supabase/bootstrap_super_admin.sql`. Файл не выполняется из Flutter и не включён в автоматические миграции. После этого назначения можно выдавать через проверяемый RPC.

## Оставшиеся вопросы перед production

- Политика удаления аккаунта, сроков хранения и анонимизации сообщений/аудита: сейчас контент удерживает ссылки на автора и препятствует каскадному удалению важных записей.
- Список полномочных владельцев инфраструктуры, процедура восстановления при удалении последнего roles.manage-назначения. Текущий RPC не предотвращает такую административную самоблокировку.
- Канал уведомления клиента об отзыве членства/прав и очистка отображаемого состояния без ожидания возврата приложения.
- Вложения и аватары: отдельные закрытые Storage buckets, MIME/размеры/проверки загрузок; до реализации публичных buckets нет.
- Auth rate limits, CAPTCHA и правила модерации. Ограничение send_message в SQL является лишь базовой защитой частоты.

## Управление чатами: миграция 9

`admin_chat_rooms` и `admin_save_chat` доступны authenticated только при `chats.manage` для прихода; гости не имеют EXECUTE. `admin_parishes` учитывает и пользовательскую роль, содержащую только chats.manage. Клиентский expected_user — защита от смены аккаунта, а не источник полномочий: сервер сравнивает его с auth.uid(). Прямые INSERT/UPDATE chat_rooms отозваны, DELETE не разрешён.

Групповая отправка требует chat.send, канал требует channels.publish; обе операции также требуют can_read_room и отсутствия архива. Закрытый access сохраняется при редактировании. Архив оставляет историю доступной тем, кто имеет право читать комнату. Удаление членства по-прежнему отзывает приходские роли и приглашения. Аудит правок содержит только revision/archived, без текста описаний или сообщений.

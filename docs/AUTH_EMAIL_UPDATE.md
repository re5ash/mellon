# Регистрация, письма и восстановление пароля

## Что входит в обновление

- В регистрации: повтор пароля, показ/скрытие пароля, переход к подтверждению почты после регистрации без сессии.
- Во входе: «Забыли пароль?» и «Подтвердить почту / отправить письмо повторно».
- Отправка и повторная отправка через Supabase Auth, понятная обработка лимитов и ошибок доставки.
- Подтверждение по коду из письма или по ссылке с дополнительным нажатием «Подтвердить».
- Новый пароль после успешной серверной проверки recovery-токена; обычный вход или подтверждение регистрации не открывают эту форму.
- Неверный, использованный или просроченный токен: ошибка и возможность запросить новое письмо.
- Русские шаблоны двух писем с одноразовым кодом и ссылкой.

Доставка на ваш реальный адрес ещё НЕ проверена. В удалённом проекте Supabase настройки не изменялись: доступа к нему и SMTP-реквизитов у исполнителя нет. HTML-шаблоны и локальный config.toml сами по себе не меняют настройки облачного Supabase.

Откройте проект `moy-prihod-dev` (`zqeuvukmkmezxuxfiwsd`).

|---|---|

Существующие требования к сложности пароля, CAPTCHA и повторной проверке безопасности не ослабляйте. Если они уже включены, сообщите об этом: может потребоваться соответствующая форма в клиенте. Файл `supabase/auth-email-settings.example.json` содержит эквивалентные поля Management API для администратора. Это образец, не команда загрузки и не секретный конфиг.

### Адрес приложения

В Authentication → URL Configuration:

- Пока тестируем на Mac: **Site URL = `http://localhost:8080`** — без завершающего `/`, без `#` и без параметров.
- В Redirect URLs сохраните существующие адреса; добавьте `http://localhost:8080/`, если его нет.
- `AUTH_REDIRECT_URL` в `config/development.json` остаётся `http://localhost:8080/`.
- На телефоне `localhost` ведёт на сам телефон! Пока Web не размещён, откройте письмо на Mac или введите код из письма вручную в запущенном приложении.
- После публикации Web: Site URL должен быть фактическим HTTPS-адресом приложения без завершающего `/`; добавьте точный адрес с `/` в Redirect URLs и задайте его в конфигурации соответствующей Web-сборки. Не указывайте домен Supabase как адрес интерфейса.

Новые шаблоны ведут на **Web-страницу** через Site URL независимо от устройства отправки запроса. В Android-приложении можно вводить код. Автоматический возврат из письма в Android-приложение этим обновлением не добавляется.

### Шаблоны писем

В Authentication → Email Templates / Emails:

1. Откройте **Confirm signup**. Тема: `Mellon — подтверждение почты`. Вставьте целиком содержимое `supabase/templates/confirmation.html` из VS Code. Сохраните.
2. Откройте **Reset password**. Тема: `Mellon — восстановление пароля`. Вставьте `supabase/templates/recovery.html`. Сохраните.

Не заменяйте `{{ .Token }}`, `{{ .TokenHash }}` и `{{ .SiteURL }}` своими значениями — их подставляет Supabase. Текст «15 минут» соответствует серверному сроку 900 секунд; при изменении срока меняйте и текст шаблонов.

Письма, отправленные до обновления шаблонов, имеют другой формат. Для проверки новых сценариев запросите новые письма. Ошибки старых Web-ссылок перенаправляются на страницу повторного запроса. Успешный старый recovery-callback не даёт доступ к новой форме: запросите новое письмо или используйте код.

## 3. Доставка — почтовый сервис и Supabase

Нужен почтовый сервис с SMTP и разрешённым адресом отправителя. Встроенная тестовая отправка Supabase ограничена адресами команды проекта и лимитами, поэтому не подходит для регистрации прихожан.

Если почтовый сервис уже есть, используем его. Если нет, сначала выбираем сервис и подтверждаем отправителя/домен. Не покупайте тариф до выбора и проверки условий.

В кабинете выбранного почтового сервиса:

1. Подтвердите адрес отправителя или домен согласно требованиям сервиса.
2. Для своего домена добавьте указанные сервисом записи SPF/DKIM; настройте DMARC. Проверяйте статус подтверждения в его кабинете.
3. Получите SMTP host, port, username, password. Отключите отслеживание переходов в служебных письмах, чтобы оно не переписывало ссылки.

В Supabase → Authentication → SMTP Settings:

| Поле | Что вводить |
|---|---|
| Enable custom SMTP | Включить |
| Sender email | Подтверждённый адрес отправителя |
| Sender name | Mellon |
| Host | SMTP-сервер вашего почтового сервиса |
| Port | Порт из инструкции сервиса |
| Username | SMTP-логин |
| Password | SMTP-пароль/ключ, только в этой панели |

Не вставляйте SMTP-пароль, service_role или Management API token во Flutter, `development.json`, исходники, скриншоты или чат. Сохраните настройки. Проверьте лимит писем в Authentication → Rate Limits согласно квоте провайдера; не снимайте ограничения полностью.

Сохранённые настройки не доказывают доставку. Её подтверждают получение реального письма и журнал почтового сервиса. При ошибке смотрите Supabase Auth Logs и журнал доставки: неверные SMTP-реквизиты, неподтверждённый отправитель, лимит, отклонение или попадание в спам требуют разных действий.

## 5. Приёмка в браузере

Используйте отдельный тестовый аккаунт и два окна браузера. Пароли, коды и полные ссылки не присылайте.

| Проверка | Ожидаемый результат | Реальный результат |
|---|---|---|
| Регистрация с несовпадающими паролями | Запрос не уходит; понятная ошибка | Не проверено |
| Регистрация новой почты | Экран подтверждения; письмо получено | Не проверено |
| Вход до подтверждения | Supabase отклоняет вход; предлагается подтвердить почту | Не проверено |
| Ссылка регистрации → «Подтвердить» | Почта подтверждена, можно продолжить | Не проверено |
| Повторное открытие использованной ссылки → «Подтвердить» | Ошибка, можно запросить новое письмо | Не проверено |
| Новый запрос, код вместо ссылки | Сервер подтверждает почту | Не проверено |
| Повторная отправка до 60 секунд | Кнопка заблокирована, показан отсчёт | Не проверено |
| Повторная отправка через 60 секунд | Приходит новое письмо; используем его код | Не проверено |
| Неверный код | Ошибка без доступа к смене пароля | Не проверено |
| «Забыли пароль?» с существующей почтой | Нейтральное сообщение; реальное письмо | Не проверено |
| Несуществующая почта | Нейтральное сообщение без утверждения о наличии аккаунта | Не проверено |
| Recovery-ссылка в другом браузере | Дополнительное подтверждение → форма нового пароля | Не проверено |
| Recovery-код в приложении | Форма нового пароля после проверки сервера | Не проверено |
| Несовпадающие новые пароли | Сохранение заблокировано | Не проверено |
| Старый пароль в качестве нового | Понятная ошибка от Supabase | Не проверено |
| Новый пароль сохранён, выход и вход | Новый работает, старый отклонён | Не проверено |
| Просроченная ссылка/код: подождать 15 минут после отправки | Ошибка срока действия, нового пароля в форме нет | Не проверено |
| Запрос нового письма после истечения | Сценарий снова проходит | Не проверено |
| Прямой переход /#/auth/new-password без проверки | Предложение запросить письмо, без формы | Не проверено |
| Обновление страницы нового пароля | Без сохранённого разрешения предлагается новое письмо | Не проверено |
| Смена аккаунта перед сохранением | Пароль другого аккаунта не меняется | Не проверено |
| Нет сети при сохранении | Ошибка, можно повторить; успех не объявляется | Не проверено |

Для просроченного токена тестируйте именно серверный ответ через 15 минут, а не только изменение часов компьютера. Не уменьшайте срок действия на проекте с реальными пользователями ради проверки. Если отправка теряется, проверяйте журнал доставки, а не отключайте подтверждение почты.

## Границы реализации

- Сервер Supabase проверяет одноразовые токены, срок действия, лимиты и пароль. UI-проверки дополняют сервер, но не заменяют его.
- Recovery-проверка создаёт обычную Supabase-сессию. Допуск к новой форме хранится в памяти на 15 минут и привязан к UID; он не является дополнительной серверной ролью. После перезагрузки вкладки допуск не восстанавливается из локального флага.
- При смене пароля производится серверная проверка текущего пользователя; после успеха локальный допуск удаляется. Мгновенный отзыв всех ранее выданных access JWT этим обновлением не гарантируется.
- Пауза повторной отправки на клиенте 60 секунд действует внутри запущенного приложения. После перезапуска защиту обеспечивают серверные лимиты.
- После сетевой ошибки возможна неоднозначность: письмо/смена пароля могли быть выполнены сервером до разрыва соединения. Проверяйте последнее письмо или вход новым паролем.
- Требуются оба новых шаблона. Только установка Python-обновления без настроек облачного Auth не завершает этап.
